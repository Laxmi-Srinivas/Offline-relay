03 / THE ENGINEERING

A local path.
No internet detour.

Flutter handles the interface and conversation state. Native Bluetooth adapters handle discovery and direct peer-to-peer message transport.

▯RequesterFlutter + native BLE
BLUETOOTH LOW ENERGY

Direct, nearby text exchange

▯HelperFlutter + native BLE

Small messages, clear boundaries. The shared message envelope has a 256-byte limit. The native adapters frame the bytes for BLE and use acknowledgements for transfer handling.

Availability on Android. A foreground service supports helper availability and request notifications while the UI is detached. Actual background behavior still needs security checks on devices.

Both nearby people need Onya installed beforehand. This connection does not give the requester Internet access. Automatic ordering, ride booking, Internet relay and a structured task system are not implemented. Android–iPhone interoperability has not been verified.

04 / SECURITY BY BOUNDARY

A request is a choice.
A chat is a session.

We reviewed the actual chat path and hardened the places where trust changes—not hypothetical future features.

Implemented Android controls on the Security branch
01 / CONSENT

No approval.
No chat.

Approval checks gate chat. Connection requests stay stable, and decisions must match the current request.

02 / SESSION BOUNDARIES

A new connection.
A clean boundary.

Current-connection matching and stale-event guards stop an old approval or message from changing a replacement conversation.

03 / RESOURCE CONTROL

Temporary chat.
Bounded work.

Bounded memory and queues, recent duplicate suppression, chat/draft cleanup, operation timeouts and notification cooldowns.

↳

The limits matter, too. Actual Bluetooth encryption and authentication remain unverified. End-to-end encryption is not established in the inspected committed code. Peer names are self-asserted.
