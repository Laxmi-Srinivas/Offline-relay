03 / THE ENGINEERING

A local path.
No internet detour.

Two platform builds preserve their working flows. Flutter handles the UI; Kotlin/Android BLE and Swift/CoreBluetooth handle nearby messages. Use two Android phones or two iPhones.

▯RequesterFlutter + native BLE
BLUETOOTH LOW ENERGY

Direct, nearby text exchange

▯HelperFlutter + native BLE

Small messages, clear boundaries. The shared message envelope has a 256-byte limit. The native adapters frame the bytes for BLE and use acknowledgements for transfer handling.

Availability on Android. A foreground service supports helper availability and request notifications while the UI is detached. A separate iOS helper implementation uses CoreBluetooth background availability and local request notifications; operating-system limits still apply.

Both nearby people need onya installed beforehand. This connection does not give the requester Internet access. Automatic ordering, ride booking, Internet relay and a structured task system are not implemented. Android ↔ iPhone communication is not supported in this hackathon submission.

04 / CLEAR BOUNDARIES

A request is a choice.
A chat is a session.

Both mobile flows require the helper to accept a request. Security capabilities differ between the preserved platform builds.

01 / ANDROID

Automatic
encrypted chat.

Ephemeral X25519 keys, HKDF and AES-GCM protect chat and End Chat messages. No verification codes. Peer identity is not authenticated; active impersonation remains possible.

02 / IPHONE

Existing
iPhone chat.

The validated iOS baseline exchanges plaintext application envelopes over BLE. Application-layer encryption is not implemented there; Bluetooth link protection is unverified. Use non-sensitive demo messages.

03 / ENDING A CHAT

Disconnect.
Start fresh.

Android has End Chat and local, in-memory Report. On iPhone, the chat back button closes the connection and returns to Nearby. Neither app relays messages through a central server.

05 / EVIDENCE

Working baselines.
Honest limits.

Prior physical-device results and final integration verification have different scopes. A successful build does not establish radio behavior.

Android ↔ Android. The team previously validated encrypted chat and helper notifications on Android. The integration preserves that application and native transport.

iPhone ↔ iPhone. The iOS branch records team-reported discovery, acceptance, bidirectional chat and helper notification tests. It is preserved as a separate iOS build target.

The relocated iOS target passes Mac/Xcode compilation; a final two-iPhone regression run remains required. Cross-platform phone communication is outside the submission scope. Read sources and validation limits →
